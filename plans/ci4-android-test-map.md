- **Cross-suite:** DO enrollment + pairing + approval (both suites); removal/DO-release (mast 482-488 vs requests 310-317); exhaustion mechanism (mast daily-limit vs requests standing/approved minute).
- **Router-side vs Go/OWRT:** `device_approve`/`devices` (`identity_test.go`, integration 953-1032); request/grant/`home_internet`/`not_after`/tickets (integration 1468-1514, `requests_test.go`); usage + `grants_used` + new_apps (1532-1556, `usage_test.go`); rule CAS + scope revocation + history receipts (`service/app_rule_test.go`, `history_test.go`); bonus/router expansion (`configuration/bonus_test.go`); release (`configuration/release_test.go`). - **App decision layer vs JVM:** `appAction` precedence incl. grants/downtime/essentials (`AppEnforcementTest`, `GrantEnforcementTest`); grant charge/remaining/never-refill/round-trips (`GrantLedgerTest`); usage event semantics, gaps, DST, checkpoint replay (`UsageCounterTest`); transport/signing/nonce/downgrade (`SyncTransportTest`); payload mapping (`MastUiStateMapperTest`, `PolicyTest`); client parsing (`GrantPayloadTest`, `AppRequestsTest`, `AppRuleClientTest`).

## (b) Slimming evaluation

**ATD availability — verified 2026-10-30** via `sdkmanager --list` in the repo's own `ghcr.io/cirruslabs/android-sdk:35` image: `system-images;android-35;aosp_atd;x86_64` and `system-images;android-35;google_atd;x86_64` both exist (rev 1; android-34/36 also have ATD). Nothing we use is missing in principle:
- **Google APIs/GMS:** not exercised at runtime by either suite (no Play installs in these scripts; pairing is deep-link; `play-services-code-scanner` is linked but unused at runtime). ATD is fine.
- **Private DNS:** platform framework feature; `private_dns_mode` default `opportunistic` and DPM `disallow_config_private_dns` work on any DPM-capable build — ATD images are exactly the class used for Device-Policy/CTS testing.
- **UsageStats:** framework service present in AOSP; CTS usagestats runs on ATD.
- **DevicePolicy/Device Owner:** supported; stronger fit than `google_apis` for DPM work.
- **Candidate packages:** mast's fallback loops already tolerate missing Google apps (AOSP `com.android.camera2`/`com.android.contacts`, optional `telecom get-default-dialer` check, `com.android.deskclock`). Residual risk: on `aosp_atd` the default-dialer check may silently skip → **prefer `google_atd`** (keeps Google dialer/calendar/contacts so every current check keeps its strength); `aosp_atd` as fallback after verifying the dialer/clock candidates. Also re-verify the Wi-Fi backend quirk (`wait-emulator-router.sh` user-mode note, `test-mast-emulator.sh:115-117`) against the ATD image.

**Snapshot boot vs `-no-snapshot`:** today every run cold-boots with `-no-snapshot` and an AVD created inside the ephemeral container (~90 s observed on the GH runner, incl. 4G data-partition zeroing). Move the AVD to a docker volume next to `mast-sdk`, and take the snapshot at **"system booted, animations off, `screen_off_timeout` set, no apps installed"** (≈ 30-45 s restore). Do **not** bake the APKs in: the debug APK changes per commit, and `adb install -r` + `pm clear` per suite (~10 s) keeps state fresh. Fresh state requirements: mast needs no device owner, unpaired prefs, no `app-usage.json` (satisfied by `pm clear` after the suite's final removal); requests needs no outbox/parent-pairing state and a fresh fixture (both apps end their suites owner-less, so `pm clear` works between them). The mast mid-suite `$ADB reboot` still works on snapshot state. Snapshot save/restore needs identical emulator flags (`-gpu swangle_indirect` etc.) — pin them in one place.

**One shared emulator for both suites:** CI already runs the two scripts sequentially in one job (`ci.yml:273-278`); the second suite currently pays a second docker network + second cold boot + second DHCP wait. Run one emulator + one network for both; keep a **fresh router per suite** (router state differs — active pact vs `default_policy allow` + parent profile — and a disposable 12 MB OpenWrt container with local `apk add` is ~30-40 s, not worth a reset protocol). Saves one full boot + DHCP (~90-100 s).

**OpenWrt container → native core:** justified: neither suite asserts OpenWrt-specific behavior; the router is only the signed-policy source + upload sink. `familywardend` already ships `cgi-phone`/`cgi-app`/`api`/`release` subcommands and `core/internal/service/http.go:22` already exposes `POST /phone`, `POST /app/{op}`, `POST /api/{method}` (the R6 portable composition). Concrete plan: a **test-only** main (e.g. `core/cmd/familywardend-testrouter`) composing `service.New` with an in-memory/file `platform.Adapter` + JSON `configuration.Backend`, serving `service.Handler` on `:7700`, plus CLI shims for `usign` keygen/sign (core `usign` package — needed by `request_flow.py`'s synthetic phone) and the admin methods the scripts call (`device_approve`, `pact`, `release`, `bonus`, `device_update`, `configuration_export`, `request_answer`, `app_decision`, ...). Effort: medium (a few hundred lines of test infra + remapping ~15 router-side script commands from `uci set`/`familywarden call` to `api` methods; the address-repair stage also drops its docker second-IP trick — bind two addresses on the container). Not required for the 5-minute target (OpenWrt setup is only ~1.5-2 min/suite and the image is local); do it when the slim smoke is proven, because it also removes `apk update` network flake from KVM dispatches.

## (c) Step 2 — fake-clock Robolectric test for approved-minute exhaustion + re-pause (CI2 race)

**Files:** new `android/app/src/test/java/io/github/denogio/familywarden/GrantExhaustionTickTest.kt` (`@RunWith(RobolectricTestRunner::class)`), production targets: `AppControlService.tick()` (`AppControl.kt:167`), `UsageMonitor.sample()` (`UsageMonitor.kt:44`), `GrantLedger` (`GrantLedger.kt`), `AppEnforcer.reconcile` (`AppEnforcement.kt:80`), `AppControl.replacedDuringRead` (`AppControl.kt:119`), `Store` (`Store.kt`).

**Seams (currently the only gaps):**
1. `tick()` is `private` and self-schedules on a `HandlerThread` → make it `internal` and call it directly from the test (all state is lock/prefs-guarded; no production change to logic).
2. `tick()` calls `LocalDate.now(zone)` / `ZonedDateTime.now(zone)` directly → add one injectable `internal var nowProvider: (ZoneId) -> ZonedDateTime` on `AppControl` (default `ZoneId::now`... default `{ ZonedDateTime.now(it) }`); tests set a fixed clock. `System.currentTimeMillis()`/`SystemClock.elapsedRealtime()` are shadowed by Robolectric (`ShadowSystemClock.advanceBy`); `BOOT_COUNT` via `Settings.Global`.
3. `UsageStatsManager.queryEvents` → `ShadowUsageStatsManager.addEvents` with `ACTIVITY_RESUMED/STOPPED`, `SCREEN_INTERACTIVE`, `KEYGUARD_HIDDEN` — the same event classes the OS produced in the CI2 logs.
4. Device owner + suspension: `ShadowDevicePolicyManager` (`setDeviceOwner`, `setPackagesSuspended`, `isPackageSuspended`); fixture installed via `ShadowRuntimeEnvironment.installPackage`. Verify Robolectric 4.14 reflection of DPM suspension into the package manager; if absent, assert on DPM shadow state (equal strength for the reconcile decision).
5. Process death: new Robolectric application / new `AppControlService` instance re-reading the same prefs + `UsageJournal` file (checkpoint already atomic in `UsageCheckpoint.encode/decode`).

**Exact assertions (guarantee not weakened):**
- `Store` holds a v3 payload: fixture app `minutes=1` standing limit already exhausted + one 1-minute grant for the fixture (fresh nonce + `PolicyClock` receipt, `Store.accept`).
- tick #1 with fixture-visible events for 30 s of fake time: `grant` spend == 30_000 (only the part past the standing limit charged — mirrors `GrantLedgerTest.spendsOnlyThePartAfterTheOrdinaryLimit`), fixture **not** suspended.
- advance fake clock, more visible events: spend reaches exactly 60_000; `sample.grantRemaining[fixture] == 0`; reconcile suspends the fixture → **"approved minute is exhausted and paused again"** at exact milliseconds, no real 115 s wait.
- Re-deliver the same sync (same nonce, same payload) and tick again: grant record unchanged (60_000), still suspended → **repeated delivery cannot refill** (mirrors the `spent == 60_000` + `suspended()` double-assert of `request_flow.py:282-285`).
- Restart: new service instance after "process death"; spend ≥ checkpoint, not reset → **restart retains consumption**.
- Mid-read replacement (the CI2 race): start a tick's reads, then `Store.accept` a *different* signed payload (new nonce) before the monitor sample; `replacedDuringRead` true → tick must return without enforcing the mixed snapshot (assert: no DPM state mutation from the stale input, and the *next* tick enforces only the consistent new snapshot with its own nonce; grant either alive in the new policy or cleanly re-evaluated — never a half-policy). This is the `7e600bb` guarantee at the level that actually failed: the emulator run died because enforcement mixed a replaced snapshot, not because of slow KVM timing.
- Negative controls: no grant → exhaustion at 60_000 of the standing limit; blocked app never unpauses even with a grant.
