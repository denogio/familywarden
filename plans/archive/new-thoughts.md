# Plan: FamilyWarden — Fully Declarative nftables Architecture

> Historical design notes, not current setup instructions. Some examples and API
> assumptions were superseded. See `../../CLAUDE.md` for the current architecture.

## Core Philosophy

**One truth. One pipeline. One reconciliation model.**

Every state change — schedules, overrides, ticket expiry — flows through a single compiler:

```
read UCI + read RAM state + GC expired tickets
              ↓
      compile full nftables include
              ↓
      nft -c -f /tmp/familywarden.include.new   ← validate
              ↓
      mv /tmp/familywarden.include.new /var/etc/familywarden.include   ← atomic
              ↓
      fw4 reload
```

**No direct nft mutations. Ever.**

---

## Why Not Hybrid (direct nft for overrides)

The previous plan mixed declarative (schedules via include) with imperative (overrides via direct `nft insert/delete`). This creates:

- Rule handles as persistent references — ephemeral, reload-sensitive, wrong
- Background `sleep` processes for ticket expiry — orphans, races, PID leaks
- Two separate apply paths that can race with each other
- State that cannot be reconstructed from config alone

The 100–300ms cost of `fw4 reload` is acceptable. Parental control is not latency-critical.

## State Model

### Persistent config
`/etc/config/familywarden` — profiles, MACs, schedules. UCI. Written by LuCI.

### Transient RAM state
`/tmp/familywarden.state` — JSON, in-memory only, lost on reboot (correct behavior):

```json
{
  "overrides": {
    "alex": {
      "mode": "block",
      "expires": null
    },
    "taylor": {
      "mode": "allow",
      "expires": 1751234567
    }
  }
}
```

No handles. No runtime nft references. No cron. No daemons.

## Compiler: `familywarden reload`

This is the only function that touches nftables. Called by:
- procd on UCI change (`procd_add_reload_trigger "familywarden"`)
- `ubus call familywarden block/allow/reset/ticket` (after writing state)
- Status calls that discover expired tickets (lazy GC)

### Algorithm

```
1. Read /etc/config/familywarden (UCI)
2. Read /tmp/familywarden.state (JSON, default {} if missing)
3. Remove expired tickets from state (GC — mutate in memory, write back)
4. Generate complete nftables include to /tmp/familywarden.include.new
5. nft -c -f /tmp/familywarden.include.new  → abort if invalid, log error
6. mv /tmp/familywarden.include.new /var/etc/familywarden.include  (atomic)
7. fw4 reload
```

Steps 1–7 are serialized under a lock: `flock /var/lock/familywarden.lock`.

## nftables Include Structure

fw4 includes are injected into the existing `inet fw4` table context. Do **not** redeclare the table. The include file contains only chain and rule additions:

```nft
# /var/etc/familywarden.include
# Generated by familywarden — do not edit

chain familywarden_forward {
    # Jumped to from fw4's forward chain (see firewall include registration)
}

# Override: explicit block — unconditional, evaluated first
add rule inet fw4 familywarden_forward \
    ether saddr 00:11:22:33:44:55 \
    counter drop comment "familywarden:alex:block"

# Scheduled block — weekday evenings (20:00–24:00)
add rule inet fw4 familywarden_forward \
    ether saddr 00:11:22:33:44:55 \
    meta hour >= 20 meta day { 1, 2, 3, 4, 5 } \
    counter drop comment "familywarden:alex:scheduled"

# Scheduled block — weekday nights (00:00–06:00)
add rule inet fw4 familywarden_forward \
    ether saddr 00:11:22:33:44:55 \
    meta hour < 6 meta day { 1, 2, 3, 4, 5 } \
    counter drop comment "familywarden:alex:scheduled"
```

fw4's built-in `forward` chain jumps to `familywarden_forward` via a rule injected through the firewall include registration (see below). This is OpenWrt-native: hook into fw4's chain, don't override it.

## Overnight Schedule Correctness

### The UX problem

A user sets "block Monday 20:00–06:00". They mean: Monday evening through the night until Tuesday 06:00.

The naive rule `meta hour < 6 meta day { 1 }` (Monday only) is wrong — at 02:00 Tuesday, `meta day` is 2 (Tuesday), so the rule does not match.

### Correct expansion

The compiler must expand overnight schedules into two rules with correct day sets:

```
Input: block day=Monday, start=20:00, end=06:00

Evening rule:  meta hour >= 20 meta day { 1 }          (Monday 20–24)
Morning rule:  meta hour < 6   meta day { 2 }          (Tuesday 00–06)
```

For a Mon–Fri schedule:
```
Evening rule:  meta hour >= 20 meta day { 1, 2, 3, 4, 5 }   (Mon–Fri 20–24)
Morning rule:  meta hour < 6   meta day { 2, 3, 4, 5, 6 }   (Tue–Sat 00–06)
```

The compiler shifts the morning-side day set by +1, wrapping Sunday (0) correctly.

Daytime schedules (start < end, e.g. 07:00–20:00) require no expansion:
```
meta hour >= 7 meta hour < 20 meta day { 1, 2, 3, 4, 5 }
```

## Locking

All state-mutating operations acquire an exclusive lock before proceeding:

```sh
(
  flock -x 200
  # ... read state, GC, compile, validate, mv, fw4 reload ...
) 200>/var/lock/familywarden.lock
```

This serializes concurrent calls from:
- procd reload trigger
- ubus override commands
- status/GC calls

## Init Script

```sh
#!/bin/sh /etc/rc.common

USE_PROCD=1
START=95
STOP=01

service_triggers() {
    procd_add_reload_trigger "familywarden"
}

start_service() {
    /usr/libexec/rpcd/familywarden reload
}

reload_service() {
    /usr/libexec/rpcd/familywarden reload
}

stop_service() {
    rm -f /var/etc/familywarden.include
    fw4 reload
}
```

## Firewall Include Registration (postinst)

```sh
#!/bin/sh
[ "$1" = "configure" ] || exit 0
uci get firewall.familywarden > /dev/null 2>&1 && exit 0
uci add firewall include
uci set firewall.@include[-1].name='familywarden'
uci set firewall.@include[-1].fw4_compatible='1'
uci set firewall.@include[-1].path='/var/etc/familywarden.include'
uci commit firewall
```

Corresponding `prerm` removes the entry on uninstall.

## Ticket Expiry — Lazy GC, No Daemon

Tickets are not expired by a timer. They are expired lazily:

- On every `reload` call, the compiler GCs expired tickets before generating the include
- On every `status` ubus call, expired tickets are removed from state and a reload is triggered
- Result: an expired ticket takes effect at the next reload (UCI change, next override action, or status poll)

This is correct for parental control — a 30-minute ticket that expires while the network is idle will be cleaned up the next time anything touches the system. No orphan processes. No race conditions.

# 4. Test scheduled block

# 6. Test ticket + lazy GC
ubus call familywarden ticket '{"profile":"alex","minutes":1}'
# Wait ~70s, then trigger any reload:
ubus call familywarden status '{}'
nft list chain inet fw4 familywarden_forward | grep alex  # should be gone

# 7. Test overnight schedule correctness
# Set Mon–Fri 22:00–07:00 schedule
# At current time (if overnight), verify drop; at 10:00 verify pass

# 8. Test atomic swap under concurrent load
